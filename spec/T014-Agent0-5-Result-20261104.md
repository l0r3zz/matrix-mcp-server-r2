## Blocker (root cause confirmed)

`run_bot` was still running on agent0-5. It syncs with the same access token, so it is the same device (`XgtvALA4RK`). It consumed every `to_device` message for that device and dropped it. Continuwuity delivers `to_device` correctly.

Proof, 2026-11-04 19:00 PST:

- `supervisorctl status` showed `run_bot RUNNING, uptime 16:27:08`. The earlier "stopped" state did not hold. Supervisor has `autorestart=true`, and a container restart brings it back.
- `/account/whoami` returns `device_id: XgtvALA4RK` for both the `run_mcp` token and the `run_bot` process token.
- Long-poll self-ping, `run_bot` running: delivered after 2 seconds (the curl won the race).
- Short-poll self-ping, `run_bot` running: `to_device: None` (the bot won the race).
- Short-poll self-ping, `run_bot` stopped: `to_device` returned the ping.

Element's `m.room_key` messages sent before this point are gone. Those old messages stay `missing_key`. New messages must decrypt.

Earlier proof chain (its Continuwuity conclusion is superseded by the run above):

- All published key material verifies offline with matrix-sdk's own `SelfSigningPubkey::verify_device_keys` (master, self-signing, and device signatures; Synapse's added `unsigned.device_display_name` is correctly ignored).
- One-time keys are claimable from Continuwuity (`/keys/claim` returned `signed_curve25519:AAAAAAAAAA4`).
- Synapse federation destinations for all five agent servers: `retry_last_ts: 0`, `failure_ts: None`. The queue is healthy.
- Element cache fully cleared (Settings -> Help & About -> Clear cache and reload); a fresh room (T014 encrypted 4) still returns `missing_key`.
- Ping test 1 (federated): `sendToDevice` from `@admin:v-site.net` on Synapse to `XgtvALA4RK` on Continuwuity, `run_mcp` stopped, incremental sync: `to_device: None`.
- Ping test 2 (local): `sendToDevice` from `@agent0-5` to its own device on the same Continuwuity: `to_device: None`.
- Reverse direction works: the agent's `send_message` and `send_direct_message` reach Element encrypted and decrypt there, so outbound to_device via federation EDU is fine.
- Room PDUs from `v-site.net` arrive in the agent's timeline (Element's `m.room.encrypted` events are visible), so the `/send` transaction pipeline is open; the `m.direct_to_device` EDU part is dropped or never queued into the local user's sync stream.

Consequence: Element's `m.room_key` to_device messages and withheld notices never reach the agent's matrix-sdk. `direct_withheld_info` stays 0, `session` holds only the 3 outbound Olm sessions the agent created toward Element's devices, and `inbound_group_session` holds only the agent's own outbound room key.

Secondary symptom: Element's profile for `@agent0-5` shows no device (stale device list), consistent with `m.device_list_update` EDUs also not propagating. A manual `/keys/query` against Synapse returns the device via on-demand fetch, which is why key structure checks passed throughout.

## Fix applied

1. Stopped `run_bot` on `agent0-5` (same-token `/sync` competition).
2. Patched `start_background_sync` in `src/matrix/client.rs` to thread `response.next_batch` (deployed; required regardless).
3. Element clear-cache-and-reload (executed; ruled out as the cause).

4. Stopped `run_bot` again on 2026-11-04 19:01 PST, and confirmed `STOPPED`.
5. Upgraded `agent0-5-continuwuity` from the 2026-04-24 build (`sha256:2688ae09...`) to the 2026-09-28 build (`sha256:c9c62bc5...`). The upgrade did not fix the fault, and it was not needed for this fault. Data backup: `/opt/agent-zero/agent0-5/mhs/continuwuity-data.bak-20261105-030027` on g2s.

6. `run_bot` restarted at 03:06 UTC. The am-ctl health engine did it. The bot check failed, and `health_engine.py` runs `supervisorctl restart run_bot` (up to `max_retries`). The fleet cycle runs every 300 seconds and checks only agents with `status == "active"`.
7. Set agent0-5 to `maintenance` with `PUT /api/v1/agents/agent0-5 {"status":"maintenance"}` at 03:22 UTC. Stopped `run_bot` again. It stayed `STOPPED` through the 03:26 cycle. Agent0-5 has no fleet health checks or alerts until its status is `active` again.

8. `maintenance` was not enough. The in-container `/a0/usr/workdir/watchdog.sh` (v3) is launched by `startup-services.sh` at boot. It runs every 120 seconds and posts `POST /api/v1/health/agent0-5/report`. That endpoint (`am-ctl/amctl/routers/health.py`) runs `_record_check_and_act` with no `agent.status` check. A failed `process` check restarted `run_bot` at 04:23:13 UTC, after the check 2 restart. Killed the watchdog (pid 9) and stopped `run_bot` at 04:32 UTC. Both stayed down through 04:35. The watchdog returns on the next container restart.

A retry at 03:16 UTC also failed. The bot was running again. The message went to room `!yGD55Deda4sPyh5qPlm_g7TR4Dh6OzjOeyOn_5za8XA` at Megolm `message_index 3`. Element had shared that session while the bot was running, so Element will not send the key again.
